# Study — SGX or TDX (and SEV-SNP) for the signer after 2029: what changes, what does not — 2026-11-11

**Why now.** Microsoft retires the DCsv3/DCdsv3 series (the only Intel SGX VMs left on Azure) on
**2029-10-31**; new DCsv3 deployments are restricted from 2026-11-01; the recommended successors are
Confidential VMs — DCesv6 (Intel TDX) and DCasv6 (AMD SEV-SNP) — and confidential containers. None of
them offers SGX ([DCsv3 retirement guide](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/retirement/dcsv3-series-retirement)).
The project's T2 is an Azure DCsv3 VM. This study is for the auditor to think about, not a decision: it
states what in our design is bound to SGX, what a VM-level TEE would change, and what the honest label
would say in each case. The owner decides when and whether to move; the SGX line stays valid on the
operator's own FLC hardware regardless of Azure's calendar.

## 1. What the project's protection actually rests on today (SGX, process-level enclave)

| Property | How we get it with SGX | Who is the adversary it holds against |
|---|---|---|
| the seed is never readable by the host | enclave memory encrypted and inaccessible to the OS; the seed exists only inside | root in the VM (T2, non-debug launch); the hypervisor is the accepted residual (V7) |
| every signature judged by the mandate inside the TEE | `signer-core` runs inside the enclave; the host only hands in a PSBT and gets a signature or a refusal | root in the VM, a BTCPay admin, the plugin |
| the operator and the auditor can check *which code* holds the seed | DCAP quote over **MRENCLAVE** (one small binary, reproducible build, ceremony-signed) | anyone who can get a quote; the owner at `init`/`attest` |
| the state cannot be swapped for another enclave's | sealing bound to MRENCLAVE (T1) / MRSIGNER+SVN (T2 path) | root in the VM |
| a restart cannot replay an old state unattended | R7 pause + owner `arm`; R9 TPM counter (needs a TPM in front of the enclave) | root in the VM |
| the TCB is small enough to be audited line by line | `signer-core` + `rcore` + the C shell + 7 pinned crates; no OS inside | the auditor's lens |

The key architectural fact: **the enclave shares the machine with its adversary.** BTCPay, the plugin,
root and the enclave live on one VM, and the design is exactly the wall between them. That is also what
makes it cheap for a merchant: one VM.

## 2. What a VM-level TEE is (TDX / SEV-SNP) — and what it is not

A Trust Domain (TDX) or an SEV-SNP VM encrypts and isolates **the whole VM** from the hypervisor and the
cloud operator. Inside the VM nothing changes: the guest kernel, root, every process see each other as
before. Attestation covers the VM's initial image and firmware (TDX: MRTD, RTMRs; SNP: the launch digest
plus the guest's claims), not one process. There is no per-process sealing primitive; Azure CVMs give
the guest a vTPM that runs in the paravisor (OpenHCL, a higher VTL inside the TD/SNP VM) and is therefore
protected from the guest OS itself, with an attestation key rooted in the CVM's hardware report
([Azure CVM vTPM](https://learn.microsoft.com/en-us/azure/confidential-computing/how-to-leverage-virtual-tpms-in-azure-confidential-vms)).

Consequence for our threat model, stated plainly: **a VM-level TEE protects the VM from the provider; it
does not protect the signer from root inside the VM.** Our adversary of record on T2 is root *inside* the
VM (THREAT-MODEL §5, the forklog incident: the attacker is the BTCPay admin on the same machine). A TDX
VM that runs BTCPay and the signer together gives that attacker the same access to the signer's memory
as today's plain VM gives — the opposite of what the project exists for. The provider, whom TDX
excludes, is the party the owner already decided to trust (V7).

So the move is not "swap the TEE"; it is **a change of architecture**:

**The signer becomes an appliance.** A dedicated small confidential VM (or a confidential container)
that runs *only* the signer daemon — no BTCPay, no shell for the operator, no admin login — and is
attested as a whole image. "Root in the VM" then means "root of the appliance", and the appliance is
built so that nobody is root at runtime (immutable image, no ssh, the only interfaces being the
signer's API and the owner's file exchange). The merchant's BTCPay VM talks to it over the network, as
the plugin already does over a Docker network today. The wall moves from "between processes on one
machine" to "between two machines".

## 3. What stays, what changes (if the appliance route is taken)

| Component | Today (SGX) | Appliance on TDX / SNP | Effort / risk |
|---|---|---|---|
| `signer-core` (mandate, classify, judge, sign, state, messages, TPM proof) | `no_std`, pure, inside the enclave | **unchanged** — it has no SGX dependency by design (hard rule 8) | none; this is the asset the whole design protects |
| `rcore` + C shell (ecalls, sealing, RDRAND, report) | SGX SDK | replaced by a thin daemon host: the same dispatcher over a local API; randomness from the OS/vTPM; **sealing via the vTPM** (keys bound to PCRs of the attested image) or via key release gated on attestation (provider in the loop) | medium; the sealing story is the hard part |
| attestation of the code | DCAP quote → MRENCLAVE of one binary; `dcap-qvl` on the owner's laptop | TDX quote → MRTD/RTMR of the **whole VM image** (kernel, initrd, rootfs); `dcap-qvl` already verifies TDX quotes; the owner pins the image measurement instead of MRENCLAVE | the reproducible-build gate becomes a reproducible-**image** gate (orders of magnitude more bytes to pin; mkosi/Nix-style builds) |
| freshness (R9) | TPM in front of the enclave: today none on Azure DCsv3 | **built in**: the CVM's vTPM is inside the TEE boundary and protected from guest root (VTL2); R9's anchor/certify path applies as is (`tss` transport) | small; R9 was designed for exactly this |
| owner key, recovery key, mandate, messages | laptop, YubiKey/TPM; files via scp | unchanged | none |
| the plugin | talks to `http://tee-signer:7390` in the compose network | talks to the appliance's address; mTLS or a tunnel between the two VMs | small |
| TCB the auditor reads | ~ a few thousand lines of Rust + SDK | the same Rust **plus** a minimal OS image (kernel, init, the daemon) — not "line by line" any more, but "reproducible and pinned" | the honest label changes: *"the code is attested as an image, not as a process"* |
| cost for a merchant | one VM | two VMs (BTCPay + a small CVM, Azure DC2es_v6-class), or BTCPay on any VM + a confidential container for the signer | the SMB pitch takes a hit; must be stated |
| provider trust | residual (V7) | the same residual, slightly smaller in theory (the hypervisor is excluded by hardware), but the vTPM/attestation plumbing (paravisor, MAA if used) is Microsoft's | label unchanged in substance |

What is **not** available on a VM-level TEE: the one-machine form. If the owner's product rule is "one
VM, the merchant's own BTCPay host", TDX does not deliver it; only SGX (on the operator's own FLC
hardware after 2029) or a different isolation story (a separate signer box, which is exactly the
appliance) does.

## 4. Three routes and their honest labels

1. **Stay SGX, leave Azure for the enclave.** T2 moves to the operator's own FLC server (Xeon E-2300 /
   Ice Lake+, physical TPM) — the design's "solves everything" row: process-level wall, MRENCLAVE
   attestation, R9 with a physical counter, no provider at all. Label: unchanged, strongest. Cost: own
   hardware and its care; not a cloud product.
2. **Appliance on Azure CVM (TDX or SNP).** The signer as an attested immutable VM image with the vTPM;
   BTCPay anywhere. Label: *"the seed is in a confidential VM nobody logs into; the code is attested as
   an image; the merchant's BTCPay host is outside the wall; the provider is a residual."* Cost: two
   VMs, a reproducible image pipeline, a new attestation pin. `signer-core` and the owner's side carry
   over untouched.
3. **Confidential container (Azure C-ACI / confidential containers on AKS).** The signer as a
   container in an SEV-SNP utility VM with a policy-attested image; the smallest operational footprint
   on Azure. Label like 2, with the container runtime added to the image TCB and Microsoft's
   policy/attestation service in the loop. Cost: platform lock-in, less control over the image.

A fourth option exists and is rejected here: BTCPay and the signer inside the same CVM. It changes the
threat model's adversary from "root in the VM" to "the provider", i.e. it protects against the party we
already trust and not against the one the product is for.

## 5. What can be done now without choosing

- Keep `signer-core` TEE-agnostic (already true; add a CI gate that it builds with no SGX-specific
  dependency — it has none today).
- Keep the **host ↔ core interface** the ecall protocol (`proto.rs`): an appliance daemon would speak
  the same requests over a local socket; the plugin would not notice.
- When the Azure vTPM exists (issue #1): R9's `tss` transport is the same code an appliance would use.
- Write the attestation pin in the owner's record as *"measurement of the attested unit"* with a kind
  tag (`enclave` today, `image` later), so the record format does not change.
- Do **not** start an image pipeline before the owner decides the product form.

## 6. Questions for the auditor

1. Do you agree that a shared TDX/SNP VM (BTCPay + signer together) is a regression for our adversary
   of record and must be excluded from the options, with only the appliance form remaining?
2. For the appliance: is "reproducible, pinned image measurement" an acceptable replacement for
   "MRENCLAVE of one binary" in your lens, and what would you require to call it audited (image
   build in a pinned container; a bill of materials; the kernel/initrd/rootfs hashes in the record)?
3. Sealing on a CVM: vTPM-bound sealing (PCR policy on the attested image) versus attestation-gated key
   release from a KMS (provider in the loop). Which keeps the label "the seed exists only inside"?
4. Does the two-VM form still fit the SMB thesis you co-wrote (key-in-hardware necessary but not
   sufficient; root cannot sign arbitrary transactions), or does it become an enterprise product?
5. Timing: with no new DCsv3 subscriptions after 2026-11-01 and retirement in 2029, when should the
   project stop investing in Azure SGX specifics (DCAP quote plumbing is reusable for TDX; the SDK shell
   is not)?
