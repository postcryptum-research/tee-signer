# FAQ

Практические вопросы о магазине BTCPay Server на кошельке tee-signer. Каждый ответ говорит, что
код делает сегодня и на каком уровне это держится; проект работает только на **signet**, и всё,
что у кода было, — внутренний цикл ревью (AI-аудитор отвечает на `REQ` каждого раунда своим
`RESP`, [`audit/`](audit/)), а не профессиональный аудит (см. последний раздел).
English: [`FAQ.md`](FAQ.md). Картина на одной странице: [`HOW_IT_WORKS_ru.md`](HOW_IT_WORKS_ru.md).

Слова, которые используются ниже:

- **анклав** — защищённый участок памяти процессора, отделённый от операционной системы
  (технология Intel SGX; у AMD есть аналог), в котором работает специальная программа. Здесь в
  ней лежат сид-фраза и выведенный из неё приватный ключ: на вход анклав получает транзакцию, на
  выходе отдаёт подписанную транзакцию — или отказ, — и ключ его никогда не покидает. Ближайший
  понятный аналог — аппаратный кошелёк вроде Ledger Nano, только встроенный в процессор сервера и
  подписывающий без кнопки, по правилам, которые задали вы;
- **`signerd`** — недоверенный демон рядом с BTCPay: загружает анклав, хранит его запечатанное
  состояние на диске, кормит заголовками блоков и даёт небольшой HTTP API; ничего не разрешает;
- **плагин** — `BTCPayServer.Plugins.TeeSigner`: обработчик выплат и страница «отправить через
  анклав»; недоверенная обвязка;
- **мандат** — что анклав имеет право подписывать, исполняется внутри анклава
  ([`POLICY.md`](POLICY.md)): доверенные адреса, лимиты на транзакцию и на окно, границы
  комиссии, структурные правила, высота окончания действия, timelock для ослаблений;
- **ключ владельца** — подписывает изменения мандата, разморозку, ротацию; на отдельном
  устройстве торговца, никогда на сервере;
- **ключ восстановления** — холодный зашифрованный файл: отменяет ожидающее изменение, заменяет
  потерянный ключ владельца, расшифровывает **блоб восстановления** (сид, зашифрованный при init
  на этот ключ);
- **квитанция** — подписанная анклавом запись о каждой подписи (номер по порядку, txid, суммы);
- **монитор** — `owner-cli monitor`, работает вне сервера: проверяет квитанции и смотрит на
  цепочку через собственную ноду торговца;
- **уровни** — T1: SGX1 без Flexible Launch Control (debug-запуск, без аттестации); T2: FLC +
  DCAP (не-debug, аттестован); T0: софт, только тесты ([`HOW_IT_WORKS_ru.md`](HOW_IT_WORKS_ru.md)).

## 1. «У меня BTCPay на одном арендованном сервере. В нём есть SGX (старый Xeon E3). Выплаты покупателям мелкие, раз в неделю перевожу в холодное хранилище. Что делать и что я получу?»

Это уровень **T1**, ради которого проект и существует. План: анклав и `signerd` как sidecar
вашего стека btcpayserver-docker; ключ владельца в TPM 2.0 ноутбука или на YubiKey
(зашифрованный файл на USB — допустимый минимум); ключ восстановления — зашифрованный файл на
двух USB-носителях в двух местах.

**1. Проверьте железо.** `cpuid` должен показывать SGX; legacy-драйвер даёт `/dev/isgx`;
работает `aesmd`. На этом классе железа анклав запускается только в **debug**-режиме (белый
список запуска Intel отменён вместе с SDK 2.28; железу с FLC он не нужен). Это и есть метка T1:
атака ноября 2026 закрыта; чего T1 **не** добавляет — защиты от root на сервере, см. «Что видит
root?» ниже, там сказано, что это значит на практике.

**2. Соберите и запустите sidecar** (скрипты dev-стека; руководство оператора — перенесённый
пункт):

```sh
# на SGX-сервере: анклав + signerd собираются в закреплённом контейнере (воспроизводимый MRENCLAVE)
docker/build-enclave.sh                     # TAG=…, RELEASE=1, SIGN=dev|ceremony → ~/tee-signer-out/<name>/
btcpay/docker/build-signerd-image.sh        # образ sidecar для btcpayserver-docker
TEE_FRAGMENT=opt-add-tee-signer.custom btcpay/docker/stack.sh gen && btcpay/docker/stack.sh up
btcpay/docker/stack.sh install-plugin       # DLL плагина, собранная в контейнере dotnet SDK
```

**3. Откройте дверь с ноутбука.** Sidecar слушает только loopback сервера (`127.0.0.1:7390`);
наружу, на сетевой интерфейс, ничего не опубликовано, через nginx ничего не идёт. Все операции
владельца ниже выполняет `owner-cli` **на вашем ноутбуке**, и ему нужно дотянуться до этого
порта, поэтому вы пробрасываете его через тот же SSH-доступ, которым администрируете сервер:

```sh
ssh -N -L 7390:127.0.0.1:7390 you@your-server        # держите этот терминал открытым; Ctrl-C закрывает туннель
```

Пока он работает, `http://127.0.0.1:7390` *на ноутбуке* — это sidecar на сервере. Это
единственный вход, и так задумано: ключ владельца на сервер не ездит никогда, ездят только
подписанные им сообщения. Ещё `signerd` требует bearer-токен в каждом запросе; он сгенерировал
его при первом старте в своём томе состояния. Скопируйте его на ноутбук один раз:

```sh
ssh you@your-server 'docker exec tee-btcpay-tee-signer-1 cat /var/lib/signerd/token' > ./token && chmod 600 ./token
```

Токен ограничивает частоту запросов и не пускает посторонние контейнеры; секретом в модели угроз
он не является (атакующий с токеном всё равно связан мандатом).

**4. Создайте ключи — на ноутбуке, никогда на сервере.** `owner-cli` собирается командой
`cd owner/owner-cli && cargo build` (на Linux нужен `libtss2-dev` для TPM и `pcscd` +
`libpcsclite-dev` для YubiKey).

```sh
B=owner/owner-cli/target/debug/owner-cli
$B keygen --role recovery --out /media/$USER/USB1/recovery.key     # спросит пароль; скопируйте файл и на USB2
# ключ владельца, один из вариантов:
$B keygen --role owner --backend tpm --handle 0x81000100            # внутри TPM ноутбука; занятый handle отвергается
ykman piv keys generate -a ECCP256 --pin-policy ALWAYS --touch-policy ALWAYS 9a 9a.pub.pem   # на YubiKey 5
$B keygen --role owner --out /media/$USER/USB3/owner.key            # минимум: зашифрованный файл, вне сервера
$B pubkey --key tpm:0x81000100        # или piv:9a, или путь к файлу — печатает публичный ключ
```

Запишите пароли в надёжное место: восстановить их нельзя. Ключ владельца и ключ восстановления —
на **разных носителях**; именно это разделение делает кражу ключа владельца ограниченной.

**5. Инициализируйте кошелёк** — один раз. Что физически происходит: `owner-cli` на ноутбуке
читает *публичный* ключ владельца из TPM (без пароля, ничего не подписывается) и *публичный*
ключ восстановления из файла и отправляет оба публичных ключа через туннель в sidecar. Sidecar
передаёт их в анклав. Внутри анклава: 256 бит аппаратной случайности превращаются в мнемонику
BIP39 из 24 слов и мастер-ключ BIP32; выводится счёт `m/84'/1'/0'`; создаётся ключ идентичности
для подписи квитанций; мнемоника шифруется на публичный ключ восстановления (**блоб
восстановления**); всё это запечатывается под этот анклав и через sidecar записывается в его том
состояния. Обратно через туннель приходит только публичное: xpub счёта, отпечаток мастер-ключа,
публичный ключ идентичности, подписанная **карточка идентичности** и блоб восстановления. Сид
через туннель открытым не проходит никогда, и ничто на ноутбуке подписывать не может. Мандата у
анклава ещё нет, поэтому до шага 7 он ничего не подпишет.

```sh
export SIGNERD_URL=http://127.0.0.1:7390 SIGNERD_TOKEN_FILE=./token      # туннель и токен из шага 3
$B init --network signet --owner tpm:0x81000100 --recovery-pk $($B pubkey --key /media/$USER/USB1/recovery.key) --out wallet.json
```

`--owner` — это *локатор*, никогда не сырой ключ: `tpm:<handle>`, `piv:<slot>` (слот YubiKey
сначала проходит аттестацию до корня Yubico и отвергается, если она не сходится) или путь к
файлу. `init` печатает уровень (здесь `T1-debug`, помечен TOFU: аттестации на этом железе нет),
xpub, отпечаток и идентичность анклава и пишет на ноутбуке `wallet.json` — карточку идентичности
вместе с блобом восстановления. Храните его; монитор и каждая следующая команда его читают.

Затем докажите, что блоб восстановления годный, **до того**, как придут деньги:

```sh
$B recovery-verify --wallet wallet.json --recovery-key /media/$USER/USB1/recovery.key
```

Это выполняется целиком на ноутбуке (туннель не нужен; в идеале на машине без сети): блоб из
`wallet.json` расшифровывается ключом восстановления, из мнемоники выводится xpub, он
сравнивается с xpub, который сообщил анклав, и печатается только «сходится / не сходится» —
никогда сами слова.

**6. Импортируйте кошелёк в BTCPay как холодный.** В настройке кошелька магазина импортируйте
`[<fingerprint>/84'/1'/0']<xpub>` (signet) как watch-only. Страница настроек плагина показывает,
совпадает ли xpub подписанта с кошельком магазина; оба пути подписи отказывают по имени, если
нет. «Показать сид», PayJoin и штатный обработчик выплат на холодном кошельке отключаются сами —
это gate (a) e2e-набора, а gate (b) проверяет, что в базе NBXplorer нет ключевого материала.

**7. Напишите и установите мандат.** Возьмите за основу пример в [`POLICY.md`](POLICY.md) §2:
дескриптор холодного хранилища как *доверенный* адрес со своими лимитами, лимиты `unlisted` для
выплат покупателям (например `maxPerTx` 1 000 000 сат, `maxPerWindow` 5 000 000 сат),
`limits.window` в 144 блока, границы комиссии, `validity.notAfterHeight` примерно на год вперёд,
`timelockBlocks` 144.

```sh
$B policy-build --json mandate.json --node-rpc http://127.0.0.1:7398 --node-cookie node.cookie --write   # заполняет chain.checkpoint, печатает хэш
$B policy-show  --json mandate.json                                   # diff с установленным (пока пусто)
$B policy-sign  --json mandate.json --key tpm:0x81000100              # nonce 0 = установка; показывает все поля, потом подписывает
$B status                                                             # installed: true, nonce 0, best_height идёт за цепочкой
```

**8. Укажите BTCPay на подписанта.** Страница настроек плагина: URL signerd
`http://tee-signer:7390` (имя sidecar в стеке), токен, минимум подтверждений, запасная ставка
комиссии. Включите обработчик выплат **TEE signer** для on-chain-выплат магазина; для ручных
отправок — **Send through the enclave**. Создайте небольшой pull payment и выплату: обработчик
соберёт PSBT, анклав подпишет, номер квитанции в `status` вырастет на единицу.

**9. Запустите монитор** на ноутбуке (или любой машине, кроме сервера), против собственной ноды,
если она есть:

```sh
$B monitor --wallet wallet.json --mandate mandate.json --node-rpc http://127.0.0.1:7398 --node-cookie node.cookie --interval 300
```

Он проверяет каждую квитанцию ключом идентичности анклава, ищет в цепочке траты с ваших адресов,
у которых нет квитанции, сверяет лимит окна, следит за лентой заголовков и при ALARM сначала
отправляет неподписанную **заморозку**, потом сообщает вам.

**Что вы получаете:** сид никогда не файл; украденный вход администратора, плохой плагин или
взломанный контейнер BTCPay могут потратить максимум бюджет неизвестных адресов текущего окна, с
лимитом на транзакцию — и монитор вам об этом скажет. Разморозить, отменить или ужесточить вы
можете с ноутбука ключом владельца; для рутинных выплат никто не должен присутствовать.

**Что нужно знать:** T1 защищает от атаки, которая случилась, — от любого, кто действует от
имени BTCPay, — но не от root на сервере; сегодняшний сид BTCPay root тоже читает, так что хуже
не становится, но и лучше на этом одном фронте тоже («Что видит root?» ниже). Если ваша угроза
включает хостера или компрометацию root, для этого есть T2. Идентичность анклава — доверие при
первом использовании (закреплена в `wallet.json`); удалённой аттестации на этом железе нет.
Сегодня только signet.

## 2. «Хочу по-настоящему: ноду, где до сида не дотянется даже root, YubiKey для ключа владельца и доказательство, что анклав — это проверенный код. Что делать?»

Это уровень **T2** — SGX с Flexible Launch Control и аттестацией DCAP: Azure DCsv3 (на нём
проект и работает) или Xeon E-2200+/Ice Lake+ с FLC, включённым в прошивке. Тот же бинарник
анклава, запущенный в не-debug режиме, и его идентичность **аттестована** и проверена на вашей
машине. Вот последовательность; что ещё не сделано — названо в конце.

**1. Анклав собирается воспроизводимо и подписывается офлайн, никогда на ноде.** Сборка идёт в
закреплённом контейнере на сборочной машине (`docker/build-enclave.sh` с `RELEASE=1`); две
независимые сборки дают один и тот же MRENCLAVE. Подпись — церемония в два шага: сборка выдаёт
хэш анклава, церемониальный ключ (RSA-3072, офлайн, под паролем) подписывает его на машине
владельца (`scripts/ceremony-sign.sh`), сборочная машина собирает подписанный анклав. Makefile
отказывает сборке, чей MRSIGNER не равен закреплённому церемониальному ключу (gate 7), чей код
содержит опрос CPU во время выполнения или чьё число LVI-митигаций ниже порога.

**2. Sidecar на ноде** использует T2-фрагмент (`/dev/sgx_enclave` + `/dev/sgx_provision`, сокет
AESM, `SIGNERD_ENCLAVE_DEBUG=false`); на маленьком диске — фрагмент стека с обрезанной нодой:

```sh
TEE_FRAGMENT=opt-add-tee-signer-t2.custom TEE_EXTRA_FRAGMENTS=opt-save-storage-xxs btcpay/docker/stack.sh gen && btcpay/docker/stack.sh up
```

**3. Ключ владельца на YubiKey 5.** Сгенерируйте его на устройстве с политиками PIN ALWAYS и
touch ALWAYS (единственные, которые `owner-cli` принимает для роли владельца), затем проверьте
аттестацию слота:

```sh
ykman piv access change-pin; ykman piv access change-puk; ykman piv access change-management-key --protect --touch
ykman piv keys generate -a ECCP256 --pin-policy ALWAYS --touch-policy ALWAYS 9a 9a.pub.pem
$B piv-attest --key piv:9a --out ./9a-attest     # цепочка до Yubico Attestation Root 1 (закреплён), политика ALWAYS/ALWAYS, серийный, ключ == слот
```

Каждая подпись владельца после этого спрашивает PIN и ждёт касания. `init` и `rotate-owner`
принимают владельца как `piv:9a` и отказывают слоту, если его аттестация не проходит:
импортированный ключ или ключ со слабой политикой владельцем стать не может.

**4. `init` с верификатором перед записью.** На T2 `init` запрашивает DCAP-quote на свежий nonce
и проверяет его на вашей машине *до* записи `wallet.json`: цепочка сертификатов до Intel SGX Root
CA, вшитого в `owner-cli`, сброшенный бит DEBUG, MRENCLAVE равен закреплённому значению, которое
вы передаёте, MRSIGNER равен церемониальному ключу, подпись карточки идентичности, nonce и статус
TCB от Intel. Рассмотренное вами платформенное advisory принимается по имени с датой и причиной,
и это принятие — часть записи:

```sh
$B init --network signet --owner piv:9a --recovery-pk … --out wallet.json \
   --expect-mrenclave <MRENCLAVE воспроизводимой сборки> --accept-advisory INTEL-SA-00615:2026-11-03:reviewed
$B attest --wallet wallet.json            # те же семь проверок в любой момент позже; --pin перезаписывает
```

Сбой на любом шаге — отказ с именем шага; запись не пишется, кошелёк вы не финансируете.

**5. Дальше как в сценарии 1:** холодный импорт в BTCPay, мандат, настройки плагина, монитор
против собственной ноды. Подумайте о `freshness.required = true` в мандате: монитор тогда выдаёт
короткоживущие свидетельские токены, и откаченный анклав *останавливается* вместо перерасхода.

**Что вы получаете на T2:** всё из T1, плюс root хоста остаётся снаружи анклава (в рамках модели
угроз SGX: побочные каналы и микрокод Intel исключены) и криптографический ответ на вопрос «тот
ли это анклав, который проходил аудит?».

**Чего ещё честно нет:** mainnet требует явного решения владельца, и в этом репозитории его не
касалось ничего; *собственное* воспроизведение аудитором закреплённого MRENCLAVE — перенесённый
пункт (на нём держится доверие к развёртыванию); руководство оператора — перенесённый пункт; и
dev-нода T2 проекта — общая VM в Azure, продуктивному развёртыванию нужна своя. Если YubiKey
используется и для других целей, его PIN общий на устройство: три неверных ввода блокируют все
слоты (разблокирует PUK), а PIN, набранный для одного ключа, вводится в тот же апплет, что и для
остальных.

## 3. Ещё вопросы

### Мой BTCPay взломали — атакующий администратор. Что он реально может?

Считайте, что он может всё, что может BTCPay, включая загрузку плагина (выполнение кода в
контейнере BTCPay) и обращение к `signerd` с токеном. Тогда он может:

- **просить анклав подписывать** — ровно как плагин, сколько угодно раз. Он получает *столько,
  сколько разрешает мандат*: неизвестные выходы до `unlisted.maxPerTx` за транзакцию и
  `unlisted.maxPerWindow` за окно в 144 блока, доверенные выходы только на *ваши* доверенные
  адреса, комиссию в границах и общий `maxOutflow` окна поверх всего. Когда окно исчерпано, анклав
  отказывает до следующего. Он не может подписать трату чужой монеты, платёж на неизвестный адрес
  сверх лимита, другой sighash или комиссию больше бюджета окна;
- **читать все файлы, которые читает BTCPay** — включая файл запечатанного состояния. Он
  запечатан под анклав; без этого анклава на этом CPU он не открывается. (Если на сервере T1 он
  получит ещё и **root**, он прочитает память анклава — ровно так же, как root читает сегодняшний
  сид BTCPay; см. «Что видит root?»);
- **ломать** — остановить ленту, удалить журнал квитанций, перезапустить `signerd` со старым
  запечатанным состоянием. Ничто из этого не ослабляет мандат. Задержанная лента останавливает
  смену окон (остаток текущего окна — всё, что есть); старое состояние — **откат** — максимум
  один лишний бюджет окна, и монитор видит, что номер пошёл назад (`SEQ_REGRESSION`), и
  замораживает. С `freshness.required` откаченный анклав вовсе не подписывает, пока вы не
  перевзведёте его.

Чего он не может: изменить мандат (нужна подпись вашего ключа владельца со следующим nonce),
разморозить, сменить владельца или вытащить сид из T2-анклава. Что делаете вы: монитор, скорее
всего, уже отправил **заморозку**; просмотрите квитанции и цепочку, вычистите сервер, затем
`unfreeze` ключом владельца — или сначала ужесточите мандат (ужесточение применяется сразу).

### Что именно анклав отвергает?

Всё, чего не может доказать. Причины — стабильные идентификаторы ([`POLICY.md`](POLICY.md) §6),
и у каждой есть вектор отказа в наборе тестов. Классы:

| Класс | Причины | Типичная причина |
|---|---|---|
| сам PSBT | `PSBT_PARSE`, `UNKNOWN_FIELD`, `TX_VERSION`, `SIGHASH`, `TOO_MANY_INPUTS`, `TOO_MANY_OUTPUTS`, `OVERFLOW` | испорченный или экзотический PSBT; sighash не `ALL` |
| входы | `INPUT_NO_PREVTX`, `INPUT_PREVTX_MISMATCH`, `INPUT_NOT_OWN`, `INPUT_FOREIGN_FORBIDDEN`, `INPUT_SCRIPT_TYPE` | нет полной предыдущей транзакции (анклав никогда не верит сумме от хоста); монета не кошелька; вход PayJoin (`rules.payjoin = none`) |
| выходы | `OUTPUT_SCRIPT_TYPE`, `CHANGE_INDEX_BEYOND_GAP`, `OPRETURN_FORBIDDEN` | сдача на индекс далеко за запечатанной границей; `OP_RETURN`, который мандат не разрешает |
| лимиты | `CAP_TX`, `CAP_WINDOW`, `CAP_UNLISTED_TX`, `CAP_UNLISTED_WINDOW`, `CAP_TRUSTED_TX(label)`, `CAP_TRUSTED_WINDOW(label)` | выплата или накопленная сумма окна выше мандата |
| комиссии | `FEE_ABS`, `FEE_RATE` | оценка комиссии BTCPay выше границ (ставка проверяется против оценки размера снизу, так что честная комиссия большой транзакции может быть отвергнута с запасом — жёсткая страховка это `maxFeeAbs`) |
| состояние | `FROZEN`, `MANDATE_EXPIRED`, `CHAIN_STALE`, `CHAIN_REORG`, `STATE_UNSEALABLE` | кто-то заморозил подписанта; прошёл `validity.notAfterHeight`; лента заголовков остановилась или реорг глубже `maxReorg`; запечатанное состояние не открывается |
| свежесть | `FRESHNESS_MISSING`, `FRESHNESS_SIG`, `FRESHNESS_TIP`, `FRESHNESS_SEQ_BEHIND` | свидетельский токен монитора отсутствует, устарел или говорит, что анклав отстал от того, что видел монитор (откат) — нужен `rearm` владельца |
| сообщения владельца | `POLICY_SIG`, `POLICY_NONCE`, `POLICY_NETWORK`, `POLICY_WALLET`, `POLICY_PENDING` | подписано не владельцем (отставным ключом, ожидающим ключом), неверный nonce, мандат для другого кошелька или второе изменение, пока одно ожидает |

Отказ ничего не списывает из бюджета. Причины возвращаются плагину (BTCPay пишет их в лог как
`tee-signer: enclave refused …`), `owner-cli sign` и в лог `signerd`.

### Почему мою выплату отвергли? Что делать?

Смотрите на причину. `CAP_UNLISTED_TX`: выплата выше лимита на транзакцию для неизвестных адресов
— разбейте её или поднимите лимит (ослабление: ждёт timelock). `CAP_WINDOW` /
`CAP_UNLISTED_WINDOW`: бюджет окна исчерпан — ждите следующего окна (144 блока от высоты начала
окна, показана в `status`) или поднимите бюджет (с timelock). `FEE_RATE`: снизьте целевую
комиссию в BTCPay или запасную ставку плагина. `FROZEN`: выясните, кто и зачем заморозил
(журнал монитора скажет), прежде чем делать `unfreeze`. `MANDATE_EXPIRED`: установите новый мандат
с более поздним `notAfterHeight`. `CHAIN_STALE`: лента заголовков sidecar от `bitcoind` лежит —
анклав не сдвинет окно, которого не видит. `INPUT_NO_PREVTX`: в PSBT нет полных предыдущих
транзакций — плагин всегда их включает; PSBT, собранный в другом месте, тоже обязан.

Обработчик выплат BTCPay повторяет попытки по своему расписанию; после десяти отказов он
отключает себя для этой выплаты, как и штатный обработчик.

### Почему изменение мандата ждёт сутки? Какие изменения применяются сразу?

**Ужесточение** — все поля движутся в ограничивающую сторону (ниже лимиты, убранные доверенные
записи, короче срок действия, длиннее timelock, `payjoin` в сторону `none` …) — применяется в
момент, когда анклав проверил вашу подпись. **Ослабление** — всё остальное, включая новый
доверенный адрес, выше лимит, другой свидетельский ключ, нового владельца — становится
*ожидающим* и активируется только на `best_height + timelockBlocks` установленного мандата.
Классификатор ошибается в сторону ослабления: поле, которое он не может доказать как ужесточение,
заставляет ждать всё обновление.

Смысл: вор с вашим ключом владельца может подать только ослабление, и за время timelock вы (или
ключ восстановления) его **отменяете**. Одно изменение в полёте за раз: пока одно ожидает, любое
следующее отвергается (`POLICY_PENDING`), включая ужесточение — ваш ответ на изменение, которого
вы не делали, это `freeze` + `cancel`, а не ужесточение поверх. `status` показывает хэш и высоту
ожидающего; каждая квитанция тоже.

### Как менять мандат в обычной жизни?

```sh
$B policy-show --json mandate-v2.json                          # поле за полем, DIFF отмечен; хэш, который вы подпишете
$B policy-sign --json mandate-v2.json --key piv:9a              # nonce = установленный + 1; PIN + касание на YubiKey
$B status                                                        # применено (ужесточение) или ожидает с высотой активации
```

Файл — это намерение; запечатанное состояние — закон. Правка JSON ничего не меняет, пока она не
подписана следующим nonce и не принята. Держите JSON установленного мандата рядом с
`wallet.json`: монитор читает из него лимиты.

### Что такое квитанция и зачем вообще монитор?

Каждая подпись возвращает квитанцию `{seq, txid, чистый отток, суммы по классам, комиссия,
высота, хэш мандата}` за подписью ключа идентичности анклава (привязан при init). Номер строго
растёт и живёт внутри запечатанного состояния. Монитор, вне сервера:

- проверяет каждую квитанцию ключом идентичности из `wallet.json` (подделанная или
  отредактированная строка журнала отвергается по имени);
- держит верхнюю отметку `(session, seq)`; тот же `seq` с другим txid — **форк** (два анклава
  из одного запечатанного состояния), меньший `seq` — **регрессия** (откат);
- сканирует ваши адреса в цепочке через независимый источник — собственную ноду или Esplora для
  signet — на **траты без квитанции** (единственное, что покажет обход анклава) и сверяет лимит
  окна с тем, что реально подтвердилось;
- следит за `best_height` анклава относительно цепочки (замершая лента через несколько проходов
  становится ALARM) и выдаёт свидетельские токены, когда мандат требует свежести;
- при любом ALARM сначала отправляет неподписанную **заморозку**, потом сообщает; `--once`
  завершается кодом 0 / 1 / 2 для OK / WARN / ALARM, чтобы cron мог вас разбудить.

Трата, которую вы просмотрели и принимаете (`--acknowledge <txid>`), перестаёт тревожить. Ключ
монитора, если он есть, может только приостановить подпись или скрыть откат — никогда ослабить
или подписать.

### Сервер умер / диск пропал / провайдер удалил VM. Монеты потеряны?

Нет. Сид существует в двух местах: внутри анклава и в **блобе восстановления**, зашифрованном
при init на ваш ключ восстановления. Расшифруйте блоб на офлайн-машине (`recovery-verify`
проверяет без печати; `--print-mnemonic` печатает, с предупреждением и набранным подтверждением)
и восстановите 24 слова в любой BIP84-кошелёк; затем переведите всё в **новый** анклавный
кошелёк, а старый считайте выведенным из эксплуатации. Новый анклав — всегда новый кошелёк: по
замыслу нет способа положить старый сид в новый анклав. Полная таблица того, что можно потерять и
что из этого следует, — [`CONTINUITY.md`](CONTINUITY.md); там же перечислено, какие учения реально
проведены (восстановление — да; потеря анклава и потеря владельца на живом кошельке — нет).

### Я потерял ключ владельца (YubiKey, ноутбук с TPM). А ключ восстановления?

**Потерян ключ владельца:** подпись внутри мандата продолжается; останавливаются изменения
мандата. `recover --recovery-key recovery.key --new-owner <локатор>` передаёт роль владельца
новому ключу **немедленно** (ключ восстановления — более сильный фактор). **Потерян ключ
восстановления при живом анклаве:** монеты целы, но страховки больше нет — `rotate-owner` не
меняет ключ восстановления, поэтому инициализируйте новый кошелёк с новым ключом восстановления и
переведите в него под мандатом. **Потеряны оба:** монеты пропали. Это «два из двух», на котором
стоит замысел; отсюда два носителя, два места.

### Какие устройства владельца работают и какое выбрать?

Сегодня, через `hw-signer` из TPM_sign: **Linux TPM 2.0** (`tpm:<handle>`; ключ создаётся
внутри TPM под паролем, не экспортируется; ноутбук — машина оператора) и **слот YubiKey 5 PIV**
(`piv:<slot>`; сгенерирован на устройстве, PIN + касание на каждую подпись, слот аттестован до
корня Yubico, прежде чем сможет стать владельцем). **Зашифрованный файл** (scrypt + AES-GCM) —
допустимый минимум, всегда вне сервера. Secure Enclave, Windows TPM, TROPIC01 и телефонное
приложение владельца есть в TPM_sign и здесь — поздние раунды.

Что выбрать: YubiKey для всего, что держит ценность — касание это физическое присутствие на
каждую подпись, и взломанный ноутбук без вас не подпишет. Ключ в TPM привязан к ноутбуку и
запечатан только паролем (не состоянием загрузки, обозначено): вредонос с вашими правами на этом
ноутбуке мог бы им воспользоваться — ограниченно, как всегда, timelock'ом и ключом
восстановления. Ключ владельца сам по себе никогда не является ключом для кражи.

### Что видит root на сервере? В чём реальная разница T1 и T2?

Начнём с сегодняшнего дня. Сид горячего кошелька BTCPay лежит в базе NBXplorer; процессы BTCPay и
NBXplorer работают от обычного сервисного пользователя, **не от root**, и свободно его читают.
То есть сегодня сид читает этот пользователь, любой, кто вошёл администратором BTCPay, любой
плагин — и, разумеется, root.

**T1** (SGX1 без FLC) переносит сид в анклав. Пользователь BTCPay, администратор, плагин,
контейнер прочитать его больше не могут — атака, которая случилась, закрыта. Чего T1 **не**
меняет — это root: на таком железе анклав работает только в debug-режиме, и root может прочитать
память debug-анклава через отладочный интерфейс SGX, как раньше мог прочитать сид. Root не
получает ничего нового; все, кто ниже root, теряют доступ. Если ваша угроза — «кто-то залез в мой
BTCPay», T1 — ответ на сервере, который вы уже арендуете. Если ваша угроза включает хостера или
компрометацию root, T1 недостаточно, и как достаточное оно не продаётся — для этого есть T2.

**T2** (FLC + DCAP): не-debug запуск, память зашифрована и недоступна root'у, идентичность
аттестована. Root всё ещё может удалять файлы, останавливать демон, задерживать заголовки или
подсовывать старое запечатанное состояние — всё это анклав и монитор превращают в отказы, паузы
или тревоги, но никогда в подпись вне мандата.

`status` говорит, что у вас (`tier: T1-debug` / `T2-release`); перепутать нельзя, и карточка
идентичности тоже несёт уровень.

### Работает ли на mainnet? Lightning? PayJoin?

**Mainnet:** пока нет — только signet; mainnet требует явного решения владельца и пунктов
развёртывания выше. **Lightning:** вне рамок; это on-chain горячий кошелёк. **PayJoin:** не в
v1 — анклав отвергает чужие входы (`rules.payjoin = none`), а PayJoin-приёмник BTCPay на холодном
кошельке выключен; в мандате уже есть правило `inflow-only` для позднего раунда через upstream
интерфейс подписанта. P2TR (`m/86'`) и PSBT v2 — тоже поздние раунды.

### Сколько занимает подпись и сколько это стоит?

Подпись — один ecall: разбор, суждение, запечатывание, подпись — доли секунды в прогонах на signet
на обоих уровнях; расписание обработчика выплат доминирует. Никакой платы за подпись нет. Стоимость — это
железо: сервер T1 — дешёвое железо, которое вы, вероятно, уже арендуете; T2 — VM Azure DCsv3
или железо с FLC. Таблицу замеров проект не публиковал; перенесённый пункт об измерении — в
[`audit/CONDITIONS.md`](audit/CONDITIONS.md).

### Это проходило аудит?

Каждый раунд — дизайн, ядро, оболочка анклава, плагин, T2, бэкенды ключа владельца, монитор —
имеет `IMPL-PASS` от внутреннего AI-аудитора, работающего по письменным запросам
([`audit/`](audit/)), с условиями, которые ведутся до закрытия в
[`audit/CONDITIONS.md`](audit/CONDITIONS.md). Каждая проверка поставляется с негативными
векторами, доказывающими, что она отказывает. Это **не** профессиональный аудит, и собственное
независимое воспроизведение сборки анклава аудитором ещё открыто. Чем больше сумма, тем больше
ревью она заслуживает. И никакой аудит не заменяет ограничений: небольшой бюджет неизвестных
адресов на окно, узкий список доверенных адресов, ключ владельца на устройстве с кнопкой, ключ
восстановления холодный и с резервной копией. Эти границы держатся, даже если баг проскочит.
