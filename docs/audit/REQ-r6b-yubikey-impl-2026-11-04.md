## 2. owner-cli changes (`owner/owner-cli/src/main.rs`, new `src/piv_attest.rs`)

- `Signer::Piv(YubiKeyPivSigner)` next to `File` / `Tpm`; `OpenKey::sign_digest` routes both hardware
  backends through one `hw_sign()` (hw-signer's shared `normalize_low_s`, then `r ‖ s`); `scalar()`
  refuses for any hardware key (the recovery key stays a keyfile: ECDH).
- `piv_locator()`: `piv:<slot>[@<serial>]`; unit-tested (`piv_locator_tests`).
- `open_piv(slot, serial, for_signing)`: opens the slot, reads its metadata, and calls
  **`owner_slot_policy_ok()` — the auditor's ship-condition (3):** the owner role accepts exactly
  PIN ALWAYS + touch ALWAYS. `Once` (one PIN per card session), `Cached` (one touch per 15 s),
  `Never` and `Default` are refused with `REFUSED: …`. The unit test
  `owner_role_accepts_only_pin_always_touch_always` walks the matrix (1 accepted, 9 refused).
  Then: touch notice on stderr; with `for_signing`, a PIN *provider* that prompts at the first
  signature.
- **`piv_pin()`:** the PIN has its own reader — `rpassword` only; **never** the `OWNER_PASSPHRASE`
  environment shortcut the keyfile `passphrase()` honours, and no local length rule (the applet's is
  6–8). It lives only in the backend's zeroized process memory for the one command.
- `keygen --backend piv` **refuses** and prints the `ykman` recipe (owner-cli never holds the
  management key, never generates or imports PIV keys).
- `pubkey --key piv:<slot>`: public key (stdout) + serial/policies (stderr); no PIN.
- **`piv-attest --key piv:<slot> [--out DIR]` — the auditor's recommendation (2), taken:** verifies
  the slot's attestation certificate through the device's f9 certificate to **Yubico Attestation
  Root 1**, pinned by SHA-256 and compiled in (`src/yubico-ca-1.pem` `9271d914…5887`,
  `src/yubico-intermediate.pem` `ec0172fe…aee1`, both fetched from `developers.yubico.com/PKI/`
  on 2026-11-04). Every link is RSA-2048 PKCS#1 v1.5 / SHA-256 (`rsa` crate); issuers must be CA
  certificates; the root is trusted by pin, not by its self-signature. Then it checks the attested
  key is P-256 and **equals the slot's public key**, the serial extension equals the device's
  serial, and the policy extension (`1.3.6.1.4.1.41482.3.8`) is exactly `03 02` = PIN ALWAYS /
  touch ALWAYS; prints firmware and form factor. Yubico attests generated keys only, so a
  verified attestation is the proof of "born on the device" that the metadata check cannot give
  ((a)-strong in the auditor's terms). Not checked: validity dates (no trusted clock on the owner's
  laptop; Yubico's attestation certificates are long-lived by design) and revocation (none
  published). Firmware < 5.7 chains to the retired `Yubico PIV Root CA Serial 263751`, which this
  verifier does not accept. Tests: the 15 pinned intermediates chain to the pinned root through
  real signatures; a tampered TBS is refused; an unpinned issuer is refused; the serial INTEGER
  parser. **Live smoke (read-only, no PIN) on the device's existing slot `9c`:** chain
  `YubiKey PIV Attestation 9c ← Yubico PIV Attestation ← Yubico PIV Attestation B2 1 ← Yubico
  Attestation Intermediate B 1 ← Yubico Attestation Root 1`, firmware 5.8.0, PIN ALWAYS / touch
  ALWAYS — the same chain the owner verified with `openssl` on 2026-11-02 for that key.

- **Attestation bound into the owner-key-SET path (the auditor's hardening after their spot-check
  of §2):** `init --owner <locator>`, `rotate-owner --new-owner <locator>` and `recover --new-owner

  to the enclave). `tpm:` reads the persistent key, a path reads the keyfile's public key; the

## 3. Owner-surface caveat (the auditor's point, recorded)

The PIV PIN is device-wide: the BTCPay owner key (`9a`) and the other project's root key (`9c`)
share it. (i) Three wrong PINs on either project block both (PUK recovery for both). (ii) The PIN
typed into owner-cli is exposed to that process, which then partially governs `9c` too — mitigated
because `9c` is touch ALWAYS (a captured PIN alone cannot sign there). True isolation needs a second
token; the owner parked that. The wrong-PIN vector is run **once**, owner present, and followed by
a correct PIN (which resets the counter to 3).

## 5. Honest label after this round

Owner key backends: encrypted keyfile (D3 floor), TPM 2.0 (`tpm:`), YubiKey 5 PIV (`piv:`), all
P-256, same 64-byte signature at the enclave. The YubiKey path adds what the TPM lacks: a per-signature
**touch** (physical presence) and a **verified attestation** of origin and policies. Residuals:
the device-wide PIN coupling of §3; no date/revocation checks in `piv-attest`; the T0 run is
mechanics evidence, the T2 rotation (§4.5) is the tier-2 evidence; and the attestation gate is
**client-side** (owner-cli), not an enclave transition rule — the enclave accepts any valid P-256
owner key ≠ recovery from the current owner, by design (backend-agnostic, no X.509/RSA in the TCB);
enclave-side attestation on rotate is labeled as a hardening for a higher tier (C-R6b-2).
